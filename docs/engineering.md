# 工程开发范式与约定

## 当前状态与选型

当前仅有文档。工程初始化时应确定下列事项，记录选择依据，并将实际命令补入 README。

| 事项 | 当前约定 |
| --- | --- |
| 框架与语言 | 待确定，结合目标消费项目和类型支持选择 |
| 包管理器 | 待确定，选定后保留一个对应锁文件 |
| 样式与变量 | 待确定，公共视觉值集中在设计变量中 |
| 预览与文档工具 | 待确定，需支持组件状态与业务组合预览 |
| 行为与视觉验证工具 | 待确定，按公共行为和验收需求选择 |
| 构建与产物 | 待确定，需明确模块格式、类型和样式入口 |
| 支持环境 | 实现前明确消费环境、浏览器及框架版本范围 |
| 发布方式 | 待确定，首期先验证本地消费能力 |

以上是待决事项，不代表已经安装、配置或验证任何工具。

UI UX Pro Max 和 Impeccable 属于开发辅助工具，不随组件运行时分发。调用方式、上下文文件及输出归属见[设计工具协作流程](design-tool-workflow.md)，接入状态见 roadmap。

## 目录与职责

首期从单一组件库工程开始。只有出现独立发布或清晰依赖隔离的需要时，再评估多包结构。

- `src/tokens/`：设计变量及其导出。
- `src/components/`：通用组件，每个组件有独立目录及使用规范。
- `playground/`：开发预览、状态示例和后台组合场景。
- `docs/`：产品、设计、工程、进度、模板与决策。

前三个目录在工程初始化时创建。测试和预览文件的具体组织随技术栈确定，优先靠近被验证的组件。

## 工程开发范式：设计与开发闭环

适用于组件、新增能力、后台组合示例和文档站界面。以[设计规范](design-system.md)中的 Editorial 最终方向为基线，工具操作详见[设计工具协作流程](design-tool-workflow.md)。本节定义开发流程，工具细则提供调用方式，二者不重复维护任务状态。

| 阶段 | 输入与工作 | 工具使用时机 | 可审阅产出与出口 |
| --- | --- | --- | --- |
| 1. 任务与契约 | 从 roadmap 选定任务，阅读产品、设计、工程和相关组件规范；确定用途、范围、API、状态和验收边界 | 先读项目上下文；不默认重新做视觉探索 | 对应组件 README／专项方案，写清约束和未决项 |
| 2. 设计与状态 | 明确信息层级、任务路径、键盘、焦点、异常恢复及状态组合；映射 Editorial 变量 | 复杂或不明确交互用 Impeccable shape；有具体证据缺口时用 UI UX Pro Max 专项检索 | 方案写回组件规范；保留采纳／舍弃理由，可指导实现与验证 |
| 3. 实现与预览 | 在实现授权范围内，复用变量、公共状态和浮层能力；提供必要状态及组合预览 | 依据已定方案实现；工具建议不能自动修改 API 或风格 | 可运行预览与实际检查命令；没有实现授权则本轮止于文档 |
| 4. 预览评审与改进 | 检查任务能否完成、层级和一致性，以及键盘、对比、溢出和边界 | critique 评审设计；audit 检查技术质量；polish／harden／distill 分别处理打磨、边界与简化问题 | 按证据记录问题、影响、修复与复验，保留必要截图；无实际预览不能记为评审通过 |
| 5. 工程与行为验证 | 执行适合改动的类型、测试、构建和浏览器检查；覆盖主要交互、长文本、空／错／加载、窄容器和字体回退 | 工具评审与人工／自动化检查互相补充 | 明确命令、环境、结果与限制；问题修复后重验受影响路径 |
| 6. 文档与交付 | 同步 API、示例、变量引用、已知限制和重要决策 | 采纳建议写回现有有效来源，避免另建主规范 | roadmap 记录已实现／已验证／已发布；提交、推送和部署按授权分别执行 |

每轮按问题规模执行必要步骤。已明确的简单交互可沿用现有契约；纯文档、仓库配置等非界面改动检查文档或配置即可，无需强行运行生图、shape、audit 或完整浏览器回归。工程实现前应解决会改变公共 API 或关键行为的未决方案；常规可逆细节由当前任务授权和项目规则处理。

### 工具选择与证据要求

- UI UX Pro Max：输入应是明确问题，例如“单色表格的半选与键盘焦点”，不再为每个组件生成两套整库风格。不使用持久化选项建立另一份主设计系统；不采纳营销 Hero、巨幅标题或与 Editorial 冲突的彩色模板。
- Impeccable：每次设计会话按实际技能要求读取一次项目 context；shape 用于方案，critique／audit 用于已有预览，polish／harden／distill 用于有依据的改进。它们是 AI 工作流程，不是引擎同名终端子命令；不能在没有源码时以 document 声称提取了已实现系统。
- 记录实际使用的工具、问题、目标文件／预览、相关建议、采纳或舍弃理由、验证结果；只使用一般规则时如实标注，不制造工具调用记录。组件内使用[规范模板](templates/component.md)记录，跨组件的决策维护现有规范和决策记录。
- 工具不可用或匹配失败时，读取现有规范并完成不依赖工具的工作，报告影响及替代依据；不得把未执行的审查写成已完成。设计评审、静态数值检查、行为测试和浏览器验收分别记录。

### Editorial 的工程落点

所有组件共用语义变量；衬线只进入标题角色，无衬线用于数据与操作。单色状态必须保留图标和说明，焦点独立叠加，禁用、加载和错误的交互规则不能由灰度推断。高级表格、日期、上传、树和暗色适配按同一方向延展，不引入其他候选的默认样式。

真实预览至少覆盖本轮改动涉及的默认、焦点、禁用、加载、错误及内容边界。G 设计稿是方向参考，不作为浏览器金样或交互证据；实际变量、真实预览和验证记录形成工程基线。精确色值与尺寸的校准同步设计规范，不在组件内私自散落数值。

## 公共 API

- 使用一致的属性、事件和状态命名，明确默认值。
- 接受外部控制的状态需说明更新方式；支持内部状态时需说明初始值及两种模式的边界。
- 明确禁用、加载、错误等属性的行为与组合优先级。
- 公共类型、组件和样式通过约定入口导出，消费方无需依赖内部文件路径。
- 扩展接口围绕具体场景设计，基础组件避免携带业务数据结构与业务服务。
- 对公共接口或默认行为的破坏性变更，记录影响范围、迁移方式与版本处理。

## 样式与依赖

- 复用公共变量，组件内部保留必要的局部布局值。
- 明确样式加载顺序、覆盖方式及对消费项目的影响，限制全局样式的作用范围。
- 依赖选型检查用途、体积、可访问性、许可和维护成本。
- 区分运行依赖、开发依赖与由消费方提供的依赖。
- 选定运行时和包管理器后记录版本要求，保证安装与构建可复现。

## 验证要求

| 改动 | 适用验证 |
| --- | --- |
| 文档 | 路径、链接、范围与状态一致性 |
| 公共 API 与类型 | 导出、默认值、类型及消费示例 |
| 交互行为 | 对用户有意义的操作、状态切换与边界 |
| 视觉 | 预览中的适用状态、长文本、窄容器与组合效果 |
| 弹层和选择类控件 | 键盘、焦点、退出及状态同步 |
| 打包与消费 | 构建产物、样式入口、类型及最小消费场景 |

自动化验证优先覆盖公共行为与回归风险。检查通过后，仅在新增改动、失败或未解决风险需要时扩大或重复验证。

当前没有运行命令。后续以实际配置为准，不使用未配置的命令作为完成证据。

## 发布准备

首次发布前确认包名、版本规则、导出入口、样式引入方式、依赖边界、许可和变更记录。通过实际消费验证后，再按用户授权执行发布。

发布结果单独记录。构建成功、本地可用、浏览器验收和外部安装可用分别验证。
